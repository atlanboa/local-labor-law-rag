# 에이전트 작업 기록

세션마다 무슨 일을 했고, 병렬이었는지, 얼마나 썼는지, 사람이 몇 번 고치라고 했는지 기록한다. 2단계에서 병렬 수와 지시문 방식을 정하는 근거로 쓴다. [roadmap.md](roadmap.md)의 두 번째 목표가 대상이다.

마지막 갱신은 2026-11-04 20:08(KST)이다. 이 기록을 만든 세션은 아직 진행 중이라 그 세션의 숫자는 그 시점까지다.

## 측정 방법

`uv run python -I scripts/session_stats.py 160 <출력 파일>`로 `~/.claude/projects/*dev-digging*/*.jsonl`을 읽는다.

- **사람 입력:** 사람이 보낸 메시지 수다. 도구 결과, 시스템 알림, 슬래시 명령 출력은 뺐다.
- **수정 지시:** 에이전트가 결과를 보고한 뒤 사람이 되돌리거나 바꾸라고 한 입력이다. 질문, 진행 승인, 막힌 것을 풀어준 입력은 세지 않았다. 사람이 메시지를 읽고 분류했다.
- **출력 토큰, 캐시 읽기:** API 응답의 `usage`를 더했다. 응답 하나가 여러 줄로 기록되므로 메시지 id로 한 번만 셌다. fork나 resume으로 복사된 줄도 한 번만 셌다.
- 모든 세션의 모델은 `claude-opus-5-5`다. 금액은 계산하지 않았다.
- 시각은 KST다. 로그는 UTC로 남는다.

## 관찰

**공유 계약을 먼저 고정하면 수정 지시가 사라진다.** 2라운드 전에 의존성, 설정, `Chunk`와 `Answer`, `get_chunks`를 커밋했다(`b1acfb9`, `69a706f`). 지시문에는 수정할 파일과 고치지 말 파일을 이름으로 적었다. 2라운드 작업자 3개는 지시 1번으로 끝났고, 범위 밖 변경도 없었다. 교훈 1, 2, 3을 뒷받침한다.

**보고만으로는 부족하다.** 2라운드는 수정 지시가 0이었지만 문제가 4건 나왔다. 2건은 병합해야 드러나는 문제였다(1번, 2번). 1건은 실제 평가를 돌려야 드러났다(3번). 교훈 6을 뒷받침한다.

**세션은 시작한 폴더에 묶인다.** 1라운드 수집 세션은 루트에서 시작했다. 그래서 worktree에서 다시 연 세션은 앞의 대화를 찾지 못했고, 보고를 복구하는 데만 세션 하나(`76dd3b4e`)와 출력 약 2만 토큰을 썼다. 2라운드는 각 worktree 폴더에서 시작해 이 문제가 없었다.

**비용 대부분은 긴 대화 세션의 캐시 읽기다.** 메인 세션이 캐시 읽기의 72%, 출력의 47%를 썼다. 사람 입력 119개의 대부분은 RAG, 법령 구조, 임베딩을 배우는 질문이었다. 대화가 길어질수록 매 응답이 앞의 대화 전체를 캐시에서 다시 읽는다. 2라운드 작업자 3개는 합쳐서 캐시 읽기 6%였다. 병렬 작업 자체보다 긴 대화가 비싸다.

**문서로 넘기면 맥락을 잃지 않는다.** 메인 세션은 11-03 20:43에 [progress.md](progress.md)를 쓰고 끝났다. 다음 세션은 그 문서만 읽고 검증을 시작했다. 검증 세션의 사람 입력 17개 중 앞 세션 내용을 되묻는 입력은 없었다. 교훈 8을 뒷받침한다.

**모델을 나눠 쓰지 않았다.** 모든 세션이 Opus였다. roadmap은 평소 작업을 가벼운 모델에 맡기라고 권한다. 2라운드처럼 계약과 범위가 정해진 작업자는 Sonnet으로 시험해 볼 만하다. 같은 지시문으로 돌려 검증 결과를 비교한다.

## 2단계에 적용할 것

- 작업자는 반드시 자기 worktree 폴더에서 시작한다.
- 지시문 전에 공유 계약을 커밋하는 방식은 유지한다. 병렬은 3개까지 문제가 없었다.
- 병합 전 검증은 보고와 별도로 한다. 병합한 상태에서 테스트를 돌리고, 평가를 한 번 실행하는 것까지 검증에 넣는다.
- 학습용 질문은 작업 세션과 따로 연다. 긴 대화 세션이 비용 대부분을 차지했다.
- 작업자 하나를 Sonnet으로 돌려 비교한다.

## 갱신 방법

라운드가 끝날 때마다 스크립트를 다시 돌린다. 새 세션을 표에 추가하고, 수정 지시는 사람 입력을 읽고 센다.
